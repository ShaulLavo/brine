# Phase 04: Persistent SQLite and R2 recovery

**Depends on:** working disposable deployment. **Goal:** app code changes never endanger database directories, and a real R2 restore is demonstrable.

**Status: Approved.** [D11](../DECISIONS.md#d11-persistent-sqlite-uses-a-mapped-app-user-and-a-host-litestream-unit) and the [persistence contract](../CONTRACTS.md#persistent-data-and-replication) fix the topology, identities, paths and tool pin. The design is complete; the implementation tasks below remain unchecked.

### Tasks

- [ ] **P04-01** Implement D11's typed runtime/database declarations, policy destination admission, immutable incarnation/database/binding/epoch identities and store reservations. Deliver D12 compatibility declarations/refusals together with the fixed schema observer, immutable marker/catalog fingerprints and affirmative empty/missing/unreadable distinctions. Add durable quiescence fences and the writer-permit startup gate; no implicit initialization. Use policy-rooted paths outside releases, runner ownership, 0700/0600 modes, explicit keep-id/User/Group and container umask 0077. Verify filesystem/mapping on Debian 13 Podman 5.4 with D11's Pi probe. Report storage use and any observed operator quota; do not claim a rootless hard quota. Integrate data mounts/facts into planning, inventory and apply so cleanup/rollback never deletes them.
- [ ] **P04-02** Implement one host runner Litestream 0.5.17 user service per database/binding with **one active replicator per destination**, a lifetime flock and store uniqueness. Use writable DB/WAL/SHM/local metadata and singular structured `replica` config. Order boot before the app without coupling app stops to replication. Test concurrent container writes, held-lock refusal, replacement/reboot and independent replica quiescence. Process started is not backup ready.
- [ ] **P04-03** Extend displayed operator enrollment to install D11's checksum-pinned amd64/arm64 Litestream tarball at its protected versioned executable path, not apt/PATH. Add version/hash inventory. The parent helper never exports its all-buckets token; child TTL is at most seven days, and operator-side renewal runs before expiry. Implement the planned agent-runnable `backup credentials rotate APP` flow with an operator-side protected parent-profile mint helper, authenticated binding-scope receipts and bounded private host delivery. Default to one operator-provisioned bucket with immutable per-database/epoch prefixes. Deliver explicitly bucket-isolated long-lived pairs or bucket-and-prefix-scoped temporary key/secret/session-token triples through immutable runner-owned 0600 environment files and expiry receipts. Use structured S3 config with no explicit key fields/URL constructor, verify session-token signing and real R2 access, and rotate/restart replication without restarting the app. Parent R2 API tokens remain operator-side. Test in-prefix access and out-of-prefix denial against real R2; keep account/bucket names private. Never expose values to apps, argv, stdout, logs, state or public artifacts.
- [ ] **P04-04** Add read-only backup status, durable remote watermark/verified restore-point evidence, lag/degraded health, credential expiry/renewal-needed and R2 network failure reporting and operational runbooks. Implement planned `prepare_restore_point` with durable fencing, quiesced SQLite backup snapshots (including fresh empty staging data), create-only R2 upload and exact-point receipts; preserve quiescence across replanning/interruption. Record protected lifecycle-verification evidence/freshness; set remote retention disabled and refuse unknown/expiring lifecycle destinations per D11. Do not equate “replicator process started” with “data safely stored”.
- [ ] **P04-05** Implement `restore test` from a recorded remote binding/epoch using structured config and mandatory fresh `-o` into isolated, nonpublic data/fixture paths. Support temporary session credentials and refuse insufficient remaining lifetime. Never write into the live DB. Run SQLite `PRAGMA integrity_check`, check a previously committed fixture sequence/marker/commit-time row and report recovered TXID/time and known/unknown loss window with Litestream 0.5.17. Support tagged LTX and immutable SQLite snapshot sources; independently verify snapshot hashes and D12 schema observations/empty proofs. Local file replicas and SDK-signing fakes do not satisfy the R2 gate.
- [ ] **P04-06** Test application replacement, reboot, proxy outage, R2 outage, missing credentials, backup retention and competing replicators, short-lived credential expiry/rotation, subordinate-UID or mode drift, and interruption after quiescence. Test the actual pinned arm64 binary/user units on the Pi; preserve scrubbed evidence. Write a separate operator-approved **live restore runbook**, not an autonomous command.
- [ ] **P04-07** Separate app migration policy from deployment: reject implicit unreviewed migrations; require an explicit migration plan, a backup/restore point and compatible rollback semantics before considering migration automation.

- [ ] **P04-08** Persistent removal, retention and purge per D8 (needs P04-01 to P04-04 and P03-09). Removal proves a fresh remote restore point, quiesces writers and replicator (including lifetime-lock ownership), and journal-renames the same-filesystem data tree under an immutable archive ID bound to incarnation, recorded paths and every replica epoch. Destination authorization/renewable credential references outlive removal; short-lived credentials may need operator renewal. A recreated app receives new incarnation and replica prefixes. Retention runs 30 days from commit with a restorable backup set throughout, and removal refuses if an R2 lifecycle rule or running replicator would break that. Expiry and `data purge ARCHIVE_ID` act by ID only, refuse live or reused paths and destinations, and purge needs `allow_agent_purge = true`. Tests: refusal by default, the retention boundary, remove-recreate-expire, active replication, and interruption during archive and purge (T22).
- [ ] **P04-09** `restore live` per D8 (needs P04-05 and P04-06): a planned, policy-gated (`allow_agent_live_restore`, default false) replacement of an app's database from a chosen backup. It takes a fresh restore point first, quiesces writers and replicator, integrity-checks the restored copy before swap-in, and recovers after interruption. Preserve the original DB/WAL/SHM/metadata bundle; resume replication with a new epoch/prefix and empty local metadata, never append older restored data into the prior LTX chain. Until this ships, live restore stays the P04-06 operator runbook.

### P04-07 policy delivery and implementation gate

**Status: Approved.** D12 and the [Schema migrations contract](../CONTRACTS.md#schema-migrations) define per-database release compatibility, a separate typed migration plan, verified restore-point prerequisites and schema-aware app rollback refusal. Migration automation is not implemented by this policy delivery.

The checkbox remains open. Current `spec.App` and `policy.Desired` have no data references, while inventory and `plan.BrineState` have no current schema evidence. `persistent_roots` permits paths but does not declare that an app uses persistence. The plan-time refusal cannot distinguish persistent apps without inventing P04-01's model. Strict v1 parsing and frozen stateless classification remain unchanged.

P04-01 must deliver the compatibility declaration and `schema_compatibility_required` conflict with persistent support, not as a later safety patch. Carry the declaration and independently observed current schema through hashes, stored inputs, plan output and apply preflight. T16 must prove incompatible manual rollback and automatic compensation refuse without restoring an old writer or changing data. Reconcile and resolve use the same current-schema proof. Only then can P04-07 be checked.

Later migration execution additionally depends on P04-04 backup evidence and P04-05 isolated restore receipts, fresh coverage of quiesced data and compatible rollback releases. Breaking migrations stay outside routine automation. D8 keeps live restore separate and policy-gated. D11's storage and replication design is unchanged by this task.

### Exit gate

Known writes survive a new app release and reboot. A real isolated restore from R2 passes database integrity/invariant checks. Live data was never touched during the restore. Recovery-point limits and failure modes are documented.

**Evidence:** T12-T16, T19, T22-T23. Asynchronous replication **cannot guarantee zero loss of last writes**; add periodic verified restore drills.
