# Phase 02: Enrolled host, Podman/Quadlet and Caddy

**Depends on:** validated spec/planner. **Goal:** support a single disposable fixture on one explicitly authorized Linux host. The authorized host is the owner's Raspberry Pi (Debian 13, arm64) within the limits in [D3](../DECISIONS.md). This is not authorization to modify the user's existing VPS.

### P02-01 evidence

The host-local collector returns the unchanged target snapshot and performs only reads. Machine-readable command output is collected from bounded stdout, separately from diagnostics. Active Caddy administration is checked independently of disk adaptation; malformed observations remain unknown. Linux file reads use nonblocking, no-follow opens and validate the opened object as a regular file or directory. Filesystem operations have context deadlines and a process-wide limit of eight outstanding workers, so even an uninterruptible kernel mount call cannot strand collection or create unbounded workers. Tests cover unrelated port owners, served domains, file-byte hashes, absent tools, failed probes, static imports and an off-loopback Caddy administration conflict. The test-only entry point is excluded from ordinary builds and CLI help. Its arm64 binary ran on the authorized Pi, strictly decoded its own JSON and passed snapshot validation. The binary was removed after the run. [Scrubbed snapshot](../../internal/inventory/testdata/pi-snapshot.json) and [probe fixtures](../../internal/inventory/testdata/pi-probes.json) retain the observed states and software versions, with synthetic identity, listeners, owner labels and disk capacity.

The Pi had no runner or active Caddy service. This verifies collection on Debian 13 arm64, not enrollment, a deployment or a working live Caddy route. Live Caddy tests use fake command responses. The collector adapts the root Caddyfile, enumerates static imports and compares the full adapted configuration against a read-only loopback administration request. Adapted JSON loses source provenance, so root domain attribution remains unknown when imports exist. Unreadable or dynamic imports and unavailable live configuration remain unknown. Quadlet image identity and allocated ports remain unknown rather than being inferred from intended configuration. Secret queries run independently of Quadlet existence when the current UID is the runner and expose names and IDs, never values. Unambiguous Brine-named secrets create secret-only app observations. A measured zero control generation and an empty unit set establish absent Brine deployment artifacts and allocations for those records, so the first-deployment planner can bind a preexisting secret. Existing or unknown control state keeps those deployment observations unknown. Ambiguous app/reference boundaries make the app set unknown instead of silently reporting an empty set.

The snapshot has no kernel, user-manager readiness or D7 home-ownership fields, so this task does not add them. It accepts an operator-provided stable identity HMAC key and a control-state generation reader. Until a control-database schema exists, a present state directory without that reader has unknown generation; a measured absent state has generation zero. Dispatcher wiring follows separately and uses `Collect(context.Context) (target.Snapshot, error)` without a dependency from inventory to dispatch.

### P02-05 remaining integration work

The package in `internal/caddy` is the generation adapter, not a deployed route or a real systemd adapter. P02-03 supplies the command implementations. P02-06 must exercise the real reload-only polkit boundary, route persistence through Caddy restart and full host reboot, and container-to-admin denial through container loopback and both generated host aliases. P02-07 remains open until its other enrollment/runtime work and live probes pass. Phase 03 must observe the served configuration and reconcile interrupted or timed-out reloads before any retry.

Local tests cover T11/T17 and the generation-files portion of T21. The read-only Caddy 2.6.2 probe accepted the renderer's multi-domain golden and whole candidate root, rejected a duplicate site with `ambiguous site definition`, and rejected an invalid directive with `unrecognized directive`. The probe used only temporary files and `caddy validate`; it did not start or reload Caddy. Its temporary directory was removed.

The main Caddyfile is passed as bytes and never modified. It needs exactly one standalone top-level `import /etc/caddy/brine/current/*.caddy` line: literal unquoted tokens, a single separating space, no continuation or trailing comment/argument. A Caddy 2.6.2 source-span tokenizer replaces only that path token; a byte-for-byte test protects all remaining operator content. Other tokens referencing the owned root, path-like snippet names, environment substitution and newer-version heredocs refuse before staging. **Other actual imports also refuse, including absolute paths:** externally imported snippets could shadow `current` on reload without shadowing the generation-path candidate. Refusing these imports avoids inspecting or trusting unowned files.

After validation, the same injected validator must run `caddy adapt --adapter caddyfile --config <candidate>` and return bounded JSON. A routing manifest of policy-validated `Site` values accompanies committed file hashes; the manager verifies its rendered bytes against the selected files rather than inferring authorization from disk. The adapted JSON must contain the pinned complete routes for every expected host and loopback port, and no stale host removed from the previous generation. Missing, duplicate, conditional or wrong-upstream routes refuse publication. Host checks walk only HTTP route matcher sets (including negation, nested subroutes and error routes), not unrelated logging fields or handler payloads. The read-only Caddy 2.6.2 validation/adaptation probe confirmed the multi-domain golden's exact route shape alongside an unrelated operator response; it touched only `/tmp` and removed its temporary directory. A follow-up read-only Caddy 2.6.2 adaptation captured a logging filter with a field named `host`; its independent JSON fixture proves that unrelated logging does not block publication. No live reload or served-state proof is claimed.

Enrollment must provide an empty `gen-0` and `current` before first publication. `Observe` returns hashes only; the operation engine must restore the routing manifest from committed desired state before applying a change. Crash states and the control-state/host-lock contract are documented in the package comment in `internal/caddy/doc.go`.

### Exit gate

A documented, manually authorized fixture starts rootlessly, is routed through Caddy, survives a **full host reboot** (a user-manager restart doesn't count, per the spike), and is not dependent on an active Brine process. Conflicts with any unrelated service abort without changes. Privilege gaps are explicitly recorded.

**Evidence:** T05, T06, T11, T17. Pin exact Podman/systemd/Caddy versions and capture redacted test output. Before real deployment, confirm the owner has explicitly authorized the *specific disposable host*.
